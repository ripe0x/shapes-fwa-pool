## Security finding S1: conditional FWA-owner oracle replacement blocks a holder exit (high, executed)

**Right and prerequisites.** A holder with a redemption pending must be able to recover value in wind-down. The real FWA owner can call `setAddr(64, oracle)`; the vault has one active listing that must be unlisted to fund that holder. The hostile oracle was deployed by this test and installed through FWA's owner-only setter on the Foundry fork. It was not present in the baseline fork or local Anvil rehearsal; FWA itself was not replaced.

**Sequence and mechanism.** On the block 26,424,971 mainnet fork, a 1 ETH holder entered, a real Shape pack was minted and listed with 0.0363 ETH backing, and redemption left `12,507,570,970,276,316` shares locked. The test impersonated FWA's owner and repointed `floorOracle` to a contract returning four ABI words, including an invalid `uint48`. `VaultLib.economics` at `src/VaultLib.sol:398-402` checks only return length before `abi.decode`; `PackVault.unlist` at `src/PackVault.sol:385-391` calls `edge()` even during wind-down. A 16,000,000-gas one-position unlist reverted on decode and left the position open. This is reachable within EIP-7825's 16,777,216-gas transaction cap. With the oracle restored, unlist, liquidation and checkpoint succeeded and the holder claimed `999,376,310,313,629,467` wei. A separate gas-burning oracle caused a three-position unlist to fail; a single-position call could still exit but consumed nearly the entire gas limit. The malformed-return case establishes the stronger one-position block while that oracle remains installed.

**Impact and limit.** The witness shows a holder exit withheld **if the FWA owner installs malformed oracle code**. It does not show a malformed oracle on the current chain or in the local Anvil rehearsal. It does not show permanent confiscation or failure once the oracle is restored. Existing `oracle_change` scenario only covers a failed/no-quote read; its draft O8 number does not cover malformed successful return bytes. The smallest repair is to bound the oracle staticcall's gas and handle malformed return data without reversion, or avoid oracle economics in wind-down/shortfall unlisting; then rerun the one-position fork witness and the normal bid/list path. Evidence: `witnesses/AuditOracleGas.t.sol`, `focused-witnesses.log`, `malformed-trace.log`, `oracle-gas-trace.log`.

## Economic and operational findings

### E1. Replaceable policy can make the keeper pay for reverted work (high, executed)

`keeper/keeper.py` gets a candidate payment through `cast call` without the signed transaction's EIP-1559 fee fields, estimates gas in a separate simulation, and sends with `minPay` at 80% of the observed candidate. A permitted owner-set `IKeeperPolicy` can return the maximum quote when `tx.gasprice==0` and zero when the actual signed transaction has a price. The vault caps the simulated quote at the deposit's processing pool, but the real call reverts `Payment` after the checkpoint path, leaving the deposit pending. A `minPay=0` call succeeds with zero pay, so this is keeper loss and delayed pricing, not a holder-fund trap by policy alone.

The fork Solidity witness establishes the conditional quote with `vm.fee(0.15 gwei)` and `vm.txGasPrice(0.2 gwei)` asserted inside a state-changing call. The local Anvil fork ran the **actual frozen production keeper** and real signed transactions with `--max-loss-wei=0`: receipt 1 used 228,848 gas, cost `15,721,292,116,592` wei, pay 0; receipt 2 used 228,860 gas, cost `15,191,307,299,620` wei, pay 0. Total billed loss was `30,912,599,416,212` wei. The keeper exited with an error after each reverted receipt, but the configured loss limit had already failed. Repetition is possible while the deposit is pending; actual duration and total loss require an operator who retries. A smaller repair is to simulate and estimate with the same fee fields as the signed transaction and stop calling `max-loss-wei=0` an absolute bound; state/inclusion races still require explicit loss accounting and an operator limit. Evidence: `witnesses/AuditMaliciousPolicy.t.sol`, `malicious-policy.log`, `malicious_policy_local.py`, `malicious-policy-local.log`, `malicious-policy-repeat.log`.

### E2. The keeper never schedules a distribution-only checkpoint (medium, executed)

`PackVault.checkpoint` permits and pays a checkpoint with no pending holder flow when a distribution is due. `keeper/policy.py:204-206` schedules checkpoints only for pending deposits or locked shares. On the real FWA fork, a 1 ETH holder was priced; a 0.04 ETH gain arrived; with no pending flow, a manual checkpoint reserved exactly `20,000,000,000,000,000` wei for distribution and paid a `56,000,000,000,000` wei keeper quote. `policy.plan` returned no checkpoint for the matching no-flow state. Without a later holder request or another caller, the distribution remains unrealized. This violates the owner's requirement that a checkpoint run when distribution is due. The smallest fix is to expose/check a due-distribution predicate and schedule the work when payable; avoid scheduling a zero-distribution checkpoint (E3). Evidence: `witnesses/AuditDistribution.t.sol`, `focused-witnesses.log`, `distribution_policy.py`, `distribution-policy.log`.

### E3. An empty checkpoint consumes the interval before a holder request (medium, independent executed challenge)

With `distributionBps>0`, `PackVault.checkpoint` accepts a no-flow call even when the computed distribution is zero, sets `lastCheckpointInterval`, returns zero pay, and closes the only checkpoint slot for that 12-hour interval. A permissionless caller used that path on the real FWA fork immediately before Alice requested redemption; the next checkpoint reverted `AlreadyCheckpointed`. The demonstrated impact is **one interval's delay per request timed after an empty checkpoint**. Once that redemption is pending, the following interval has legitimate work; indefinite repeated starvation was considered and rejected. The owner requires at least one usable exit window a day, so this timing matters even though no ETH was taken. The smallest fix is to reject a no-flow checkpoint before changing interval state unless a real distribution meeting its minimum is due. Evidence: `witnesses/IndependentChallenge.t.sol`, `INDEPENDENT.md`, `independent-challenge.log` (exit 0, 1 pass).

### E4. Keeper treats reserved checkpoint charges as redeemable cash (medium, executed)

`keeper/keeper.py:~95-118` subtracts pending deposits and four holder reserves from the vault balance but omits `processingPool`; the vault's `_free()` subtracts it (`PackVault.sol:718-720`). In a real FWA fork, a 1 ETH holder and one active pack were followed by 20 actual deposit/cancel round trips. Those retained 1,248,000,000,000,000 wei of nonrefundable charges; a later redemption added its own checkpoint charge, yielding a 1,310,400,000,000,000 wei processing pool. At the redemption threshold, actual free cash was `873,337,920,659,858,602` wei, while the keeper inferred `874,648,320,659,858,602`; owed at the last price was `873,961,920,659,858,594`. The vault therefore had a **623,999,999,999,992 wei** cash shortfall, but `policy.plan` scheduled only `checkpoint`, no liquidation. After that keeper-only checkpoint, `30,795,908,428,557` shares representing approximately `310,689,548,969,079` wei at the new estimate remained locked. Rewinding to the same fork state, one real Shape liquidation before the checkpoint fully filled the redemption. The observed harm is a **one-interval delay of that value**, not asset loss or perpetual trapping. The cancellations cost their caller 0.001248 ETH in retained charges; the witness does not show a costless attack. Repair the keeper balance read to subtract `processingPool`, then test the actual keeper path at this threshold. Evidence: `witnesses/AuditFreeMismatch.t.sol`, `free-mismatch.log`, `free_mismatch_policy.py`, `free-mismatch-policy.log`.

### E5. Keeper activation batch exceeds Ethereum's transaction gas cap (medium, executed)

When FWA has an unresolved acquisition, new pack listings are staged and earn no active-listing fee. Its verified `activateListings(maxCount)` drains staged listings once the queue is clear. `keeper/policy.py:~199-202` passes **every** staged vault ID in one call and sets `maxCount=200`; it has no batch split. A real-VRF fork sequence left 100 new vault packs staged while the FWA queue was busy. After the real queue drained, `policy.plan` chose `activate(100 IDs, 200)`. The vault call failed with 16,000,000 gas (below EIP-7825's 16,777,216 limit). In Foundry only, a deliberately over-limit allowance let the identical call complete at **26,443,789 gas**; a 10-ID/10-max call succeeded within the cap. The live limit means the keeper cannot submit its planned 100-ID call, and repeating it will not activate them. The 100 packs represent 3 ETH of Shape value plus about 3.63 ETH posted backing in this witness, sitting idle in FWA custody until someone uses smaller batches; this is not a proven permanent loss or a 2 ETH canary-state failure. The larger state is permitted once the admin raises `tvlCap`/`maxPositions` within bytecode bounds. The smallest repair is to cap both the ID list and FWA `maxCount` to a measured safe batch, then test consecutive batches to full activation. Evidence: `witnesses/AuditActivationGas.t.sol`, `activation-gas.log`, `activation-gas-100.log`, `activation-gas-100-confirm.log`, `activation_policy.py`, `activation-policy.log`.

### E6. An expired allocation can be priced below its reclaimable value, diluting earlier holders (medium, executed)

`VaultLib.valueOpen` marks any `LISTING_ALLOCATED` at the lesser of pack value or net backing (`src/VaultLib.sol:102-125`). It does not distinguish an open purchaser window from an **expired** one. After expiry, the verified FWA route lets the depositor reclaim net backing, and `VaultLib.sync` actually does so. A permissionless caller can nonetheless checkpoint before `sync`, and a pending new deposit mints shares against the low price. The witness's `allocatedBoundBps=200` (2%) guard allowed this one allocated pack in a 30-position vault; `deploy/canary.example.json` sets 1,000 (10%), so the executable transfer is not a canary maximum.

The real VRF fixture at block 26,417,086 selected the vault's pack. After the 1-hour purchaser window elapsed, FWA's real public processor drained the acquisition queue; the listing remained allocated until `sync`. Its pack value was **0.03 ETH**; reclaimable backing was **0.035937 ETH**. With a 3 ETH dead-share seed, 30 live positions, a 1 ETH prior holder and a 1 ETH new depositor, the test compared two fork snapshots differing only in whether `sync` occurred before or after the new depositor's checkpoint. Both sync calls paid the keeper exactly `30,000,000,000,000` wei. The prior holder's later actual claim was `946,216,954,764,273,047` wei with late sync versus `946,480,058,845,274,974` wei with early sync: **263,104,081,001,927 wei shifted away from that holder**. The new depositor's remaining share value was `1,121,147,712,226,175` wei higher with late sync; the dead-share seed slice was `859,385,063,405,194` wei lower. These differences do not sum exactly because checkpoint request charges and payable balances differ between the two orderings; no unexplained absolute loss is inferred. The witness establishes timing-based dilution at this 3 ETH seed/30-position scale, not a measured canary-scale maximum.

The smallest safe repair is to prevent a checkpoint from pricing an expired, reclaimable allocation as an uncertain one: settle it through the real `sync` path first, or use a value only after the right to that amount is realized. Check the exit-window and gas effect of whichever rule is chosen, then rerun both orderings and a purchaser who acts before expiry. Evidence: `witnesses/AuditAllocatedValuation.t.sol`, `allocated-valuation.log`.

### E7. Forward return model omits staged FWA custody and the activation cap (high economic evidence gap, source plus executed counterexample)

The owner's formal gate is 10% annual net return at trailing-30-day successful-selection volume, tokens zero, and a 0.5 gwei gas ceiling. The published `sim/out/forward.md` uses 442/day and reports +132.1% closed form and +78.5% mean (p5 −8.6%) for 100 positions at that ceiling. Its state also sets `queue_drained=True` on every open-interval pass. There is no FWA `STAGED` transition, activation call, or transaction gas-cap failure in the forward loop. The real fork in E5 reaches 100 staged listings, with no active fees and a keeper batch that cannot fit one transaction. Thus the published forward mean is **not parity-validated for a distinct, allowed money branch**, and the gate cannot currently be called passed on that simulation. The magnitude of correction to the 100-position, 0.5-gwei year was not calculated. As a materiality signal from a different model/window, the repository's historical 30-position, 0.15-gwei backtest fell from +313.5% annualized without staging to +168.7% with staging; those percentages must not be transplanted to the forward gate. Repair the keeper batch, model staged time/custody/gas-limit behavior, match the branch step by step against a real fork, then recompute the gate and downside at both trailing-30-day and shorter observed volume. This is an economic evidence failure, not a demonstrated negative annual return.

### E11. An allowed 63-unit pack cannot be built from empty inventory within the transaction cap (medium configuration liveness, executed)

## Asset paths and round trips

The code-derived map was sealed in `DISCOVERY.md` before prior reports were consulted. ETH enters as seed, deposit escrow, a checkpoint charge, a redemption charge or FWA fees. Deposits mint shares only after a blackout checkpoint; cancel refunds escrow but retains the checkpoint charge in `processingPool`. Shares lock on redemption; free ETH plus incoming escrow moves to `redemptionReserve`, then `claimableTotal`, then the holder on `claim`. Gain can move to `distributionReserve`, then the same claim path. Strategy ETH mints Shapes, pays mint fees, builds packs and posts backing with FWA; keep/silent returns net backing while FWA/purchaser gets the pack, bid sends backing to purchaser/FWA while the vault retains the pack. Token rewards are claimed and burned, with zero vault ETH pay for that burn. Fees/keeper payments leave the vault and do not return.

The tested round trips include deposit→checkpoint→redeem→claim, list→real FWA selection outcomes→sync/relist or liquidation, wind-down→unlist→liquidate→claim, distribution gain→reserve→claim, staged→activate, token reward→burn, and local production deployment/keeper→wind-down. `ForkReconcile.t.sol` and `sim/reconcile.py` matched the same real-VRF sequence to the wei: FWA fees received `749,287,067,792,040`, keeper pay `3,783,500,000,000,000`, mint fees `9,000,000,000,000,000`, backing lost `36,300,000,000,000,000` wei in that sequence. The local canary rehearsal mined 18 transactions, 0 reverted, had keeper pay `9,721,428,663,480,000` and gas spent `10,967,518,099,074,898` wei, and closed its ETH ledger to the wei; this rehearsal deliberately uses a V2 loss policy at the spike and is not proof of V1 keeper profitability or mainnet execution.

Monotone values include epoch, redemption era, checkpoint interval, high-water mark and distribution accumulator; pausing and wind-down are one-way operator controls; mint fees and bid backing leave one-way; token burn reduces supply one-way. Budgets consume and refill, so are not monotone. The owner rationale for every ratchet is not recorded in this audit. Cancellation's retained `processingPool` and one-wei reserves are unresolved destination questions. The production keeper's omitted `processingPool` caused the executed partial-fill delay in E4. The retained cancellation charge was exercised as deposit → cancel → later redemption checkpoint; whether surplus pool ETH is eventually distributed to the intended contributor has no explicit owner entitlement rule.

## Things that don't make sense

1. A keeper set to lose zero can spend gas on a transaction whose payment was checked only in a fee-free simulation.
2. A cancelled deposit leaves a charge reserved for a checkpoint it did not require; the keeper reports that reserved amount as free ETH and, in the fork witness, skipped a needed liquidation.
3. A permissionless empty checkpoint can consume the sole slot immediately before a holder asks to exit, while a genuinely due distribution is never scheduled by the keeper.
4. The numeric asset gate says ten draft rows are within bounds while its current owner approval is absent and the oracle-failure row does not exercise malformed successful bytes.
5. A canary labelled 2 ETH has an admin-raisable TVL cap and meaningful keeper-payment headroom under an admin compromise.
6. The keeper can plan an activation batch requiring 26.4 million gas, beyond Ethereum's transaction cap, although smaller permissionless calls work; a permitted 63-unit pack also exceeds the cap on its first build.
7. An expired allocation can be marked 0.005937 ETH below a realizable backing claim during deposit pricing, shifting value from an existing holder to the new depositor.
8. The forward model reports a passing annual return while assigning newly listed packs active status even in the FWA queue state that stages them onchain.
9. The optional keeper slowdown counts seven-day issued requests while the owner's formal economics gate counts 30-day successful selections; whether that divergence is intentional is unresolved.
10. The value-conservation invariant assumes no holder profits, then crashes when a holder receives a real donated gain.
